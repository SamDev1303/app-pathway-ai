# Atlas-AI Pre-Meeting Audit — Findings

## BLOCK (fix before 15:30)
1. "Find your match" does not open the lead form modal — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/components/Hero.tsx:72`. The primary CTA is a plain anchor to `#match`, so demo step 2 ("CTA opens lead form modal") will instead scroll to the inline toy matcher. Exact fix: make the hero CTA a client-controlled button that opens `LeadModal` directly, or change the screen-share script to click through the matcher and then the later consultation CTA.

2. Lead form submit does not redirect to `/matches/[token]` — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/components/LeadModal.tsx:257-264`. `/api/leads` returns `match_token`, but the client only sets `status="success"` and clears the draft. Sam will get a "Got it" modal instead of the ranked matches page. Exact fix: after successful JSON, run `window.location.assign(`/matches/${data.match_token}`)` before or instead of `setStatus("success")`; validate `typeof data.match_token === "string"` first.

3. Do not trigger a CLI redeploy before the meeting — `/Users/shamalkrishna/Desktop/atlas-ai/vercel.json:3` and `/Users/shamalkrishna/Desktop/atlas-ai/web/middleware.ts:4-5`. The configured Vercel production build path is `cd web && npm install && npm run build`, which Koda reports is working. A local `vercel build` path is known to fail around Edge middleware plus Supabase SSR (`web/src/lib/supabase/middleware.ts:12-36`). Exact fix before 15:30: leave the current production deployment alone; if redeploy is unavoidable, use the same Vercel project production pipeline that produced `unimate-demo.vercel.app`, not an ad hoc CLI build from repo root.

## HIGH (fix post-meeting)
1. Production env has a notification var the code ignores — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/app/api/leads/route.ts:197`. Current prod env includes `ADMIN_NOTIFICATION_EMAIL`, but the code reads `LEAD_NOTIFY_EMAILS` and falls back to `sam@claudeking.org`. Demo submission still returns 200 because email failure is non-blocking, but leads may notify the wrong inbox. Exact fix: either set `LEAD_NOTIFY_EMAILS` in Vercel prod or change the code to read `process.env.LEAD_NOTIFY_EMAILS ?? process.env.ADMIN_NOTIFICATION_EMAIL ?? "sam@claudeking.org"`.

2. `/api/chat-simple` is still pinned to a free rotating model — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/app/api/chat-simple/route.ts:50-75`. If `openai/gpt-oss-120b:free` rotates, rate-limits, or disappears, the endpoint returns 503 JSON with the fallback consultation message. The web `/chat` demo uses `/api/chat`, not this endpoint, so this should not break the 7-step screen-share, but it can break mobile/simple smoke tests. Exact fix: reuse the `/api/chat` model selector or read `CHAT_MODEL`, mapping `openrouter/openai-mini` to `openai/gpt-4o-mini`.

3. `/api/sop` returns 500 for malformed non-UUID tokens before it reaches the intended 404 path — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/app/api/sop/route.ts:339-354`. A syntactically valid missing UUID should return `{ error: "Invalid lead token" }` with 404, but a bogus string against a UUID `match_token` column can raise a Supabase/Postgres cast error and hit the 500 "Lookup failed" branch. Exact fix: validate `body.leadToken` with a UUID regex before querying; return 404 or 400 with the same user-safe "Invalid lead token" message.

4. Rate limiting is fail-open because Upstash envs are not in prod — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/lib/ratelimit.ts:25-65` and `:130-163`. `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are referenced but absent from Koda's prod env list. That means `/api/chat` and `/api/sop` skip per-IP/session/global caps. Not a meeting blocker, but it weakens the free-tier burn protection. Exact fix: add both Upstash envs in production or remove the "prod must set" comment until launch.

5. Browser/server logging still has raw `console.error` on match and SOP surfaces — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/app/matches/[token]/page.tsx:66-88`, `/Users/shamalkrishna/Desktop/atlas-ai/web/src/app/sop/[leadToken]/page.tsx:53`, `/Users/shamalkrishna/Desktop/atlas-ai/web/src/app/sop/[leadToken]/SopEditor.tsx:242`, `:278`, `:387`. The match page errors are server-side, not browser console, but they bypass the new redacting logger and can include token/error payloads. The SOP editor errors would surface in browser devtools if Sam opens that route. Exact fix: use `logger` server-side and remove client `console.error` in favour of user-visible error state plus safe metadata.

6. `/api/chat` error responses are JSON, not AI SDK UI-message streams — `/Users/shamalkrishna/Desktop/atlas-ai/web/src/app/api/chat/route.ts:365-375`. If OpenRouter or embedding/RPC code throws during the live chat question, `useChat()` may show a failed turn rather than streaming the MARA-safe fallback text. Exact fix: return the same SSE/UI-message stream format used by `deflectionStreamResponse()` for catch-path failures.
